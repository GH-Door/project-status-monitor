1. 이번에 해결하려고 한 문제와 코드 변경

가. 같은 의미의 질문에서 인용 검사 실패
앞선 실제 비교에서는 같은 승인 예산을 묻는 세 문장 중 한 문장에서 원문 연결 검사가 실패했다.
기존에는 모델이 문서 ID와 줄 ID를 함께 출력했다. 이번에는 서버가 현재 제공하는 유효 원문 줄에
1, 2, 3… 번호를 붙이고, 모델은 그 범위 안의 정수만 선택한다.
문서 ID·줄 ID·인용문은 서버가 선택된 번호에서 복원한다. 빈 줄·표 구분선은 선택 대상에서 제외한다.
구조화 출력은 존재하지 않는 번호, 문자열 ID, 누락된 항목 등을 거부한다.
서버에서도 항목별로 재검사하여, 잘못된 항목 때문에 다른 정상 항목의 답변까지 버리지 않는다.
인용 연결 실패(citation_error)는 자료 부족(missing)과 구분하여 기존 화면·대화 저장 경로에 전달한다.
파일: src/psm/answer_contract.py, src/psm/llm.py

주의: 번호가 유효하다는 사실만으로 답변의 사실관계가 증명되지는 않는다.
다른 기간의 유효한 원문 번호를 고르는 것 같은 의미 오류는 여전히 평가가 필요하다.
회사·사업·항목·기간·조건, 현재 승인판, 계산 입력 근거에 대한 기존 프롬프트 검사는 유지했다.

나. 문서를 선택하면 인사까지 자료 부족으로 보류
기존 문서 선택 분기는 질문을 문서 답변 경로로 바로 보냈다.
팀원 main의 '선택 문서는 검색 범위이고, 모든 대화의 종류를 결정하지 않는다'는 방식을 반영했다.
선택 문서가 있어도 계획 단계에서 문서 질문·일반 대화·웹 질문을 구분한다.
계획 단계에는 선택한 문서 이름을 알려 주며, 실제 문서 검색에는 선택한 문서 ID 제한을 그대로 전달한다.
일반 답변이 회사 정보를 사용했다고 표시되면 문서 경로로, 최신 정보가 필요하다고 표시되면 웹 경로로 돌린다.
기존 웹 근거 확인 경로도 유지한다.
파일: src/psm/planner.py, src/psm/answering.py, src/psm/rag.py

다. 일부는 답했는데 전체 답변 성공으로 기록
앞선 비교의 '승인 예산과 실제 입금액' 질문은 예산을 답하고 입금액은 모른다고 했지만,
모델이 두 내용을 supported 항목 하나에 넣어 partial=false가 되는 문제가 있었다.
이제 답변 전에 질문의 독립 항목을 분리한다. 이 단계에서는 문서의 답을 보거나 자료 유무를 판정하지 않는다.
그다음 고정된 item_1, item_2… 항목마다 supported / missing / mismatch / conflict를 판정한다.
하나가 missing이어도 다른 supported 항목은 답한다. 두 가지를 한 항목으로 합친 출력이나 항목 생략은 거부한다.
예산 supported + 입금액 missing이면 partial=true, abstained=false로 기록한다.
모두 답할 수 없으면 전체 보류로, 잘못된 원문 연결이면 citation_error로 기록한다.
원문에 적힌 '0건', '없음', '누수 흔적은 확인되지 않았습니다' 같은 실제 값·점검 결과는
그 표현만으로 자료 부족으로 바꾸지 않는다.
기존 item_results·partial·reason_code 저장 형식을 재사용하며 대화 재조회에도 유지된다.
파일: src/psm/answer_contract.py, src/psm/llm.py, src/psm/rag.py

이미 저장된 과거 답변·잘못된 상태를 소급해서 수정하지 않았다. 변경 후 새 질문에 적용된다.
질문 분리 자체도 모델의 의미 판단이므로 모든 복합 질문을 완벽하게 분리한다고 보장하지 않는다.

5. 직접 확인하는 순서

(1) http://localhost:8000/ 에서 새로고침하고 '01_라온공간워크스'를 선택한다.
(2) 문답에서 새 대화를 연 뒤 001_사업계획_라이트.md를 선택한다.
(3) 아래 표현을 각각 새 대화에서, 그리고 이어지는 대화에서도 확인한다.
    - 현재 승인 예산은 얼마야?
    - 승인된 예산에 대해서 알려줘
    - 승인 예산은 얼마야?
    기대: 같은 현재 승인 예산 68,000,000원과 내부 비용 한도라는 의미 유지.
    단, 요청하지 않은 매출·실제 입금액으로 의미를 바꾸면 실패다.
(4) 선택 문서를 그대로 둔 채 '안녕, 오늘도 같이 일해보자!'라고 묻는다.
    기대: 일반 인사로 응답. 문서 근거 부족이라는 이유로 보류하면 실패다.
(5) '승인 예산과 실제 입금액은 각각 얼마야?'라고 묻는다.
    기대: 예산은 답하고, 선택 자료에서 실제 입금액은 확인하지 못했다고 구분.
    입금액을 청구액으로 대신하거나 0원으로 단정하면 실패다.
    저장된 결과는 예산 supported, 입금액 missing, partial=true여야 한다.
(6) 전체 문서 선택을 해제하고 최근 매출 추이를 질문한 뒤 그래프를 요청한다.
    기존의 두 표현 '이 내용을 그래프로 보여줘'와
    '이 내용을 토대로 시각화 자료를 만들어주는데 그래프로 만들어줄 수 있을까?'를 비교한다.
    기대: 원장 처리월별 VAT 제외 순공급가액, 감액 한 번 반영, 답변·표·그래프 값 일치.
    위 라온의 8월/9월 수치는 기존 6개 계약 원장 기준이며 회사 전체 입금액을 뜻하지 않는다.

실제 답변 / 인용문 / 일부 답변 표시 여부를 함께 남기면 변경 전후를 비교할 수 있다.

6. 처리 시간·비용과 구현 근거

일반 문서 근거 답변에는 질문 항목 분리용 모델 호출이 1회 추가된다(출력 상한 600토큰).
선택 문서가 있으면 질문 종류를 구분하는 계획 호출도 거친다.
따라서 일반 문서 답변의 지연·API 비용이 늘 수 있다. 성공한 항목 분리와 답변 호출의 사용량을 합산한다.
기존 서버 계산으로 완성되는 매출 답변과 후속 시각화는 질문 항목 분리 호출을 거치지 않는다.

구현 근거: OpenAI 공식 Structured Outputs 문서
https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=chat
필수 필드·타입·수치 범위를 스키마로 제한하는 방법을 적용했다.
문서도 구조화 출력의 형식 준수와 내용의 정확성을 구분한다. 이번 변경 역시
'원문 번호/항목 누락 같은 형식 오류를 줄이는 장치'이며 의미적 정답을 보장하는 검증기로 주장하지 않는다.
한국어 정답률 향상을 입증한 새 논문 실험으로 표현하지 않는다.
